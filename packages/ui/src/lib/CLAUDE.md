# `packages/ui/src/lib/` — module rationale

Why these modules are the way they are. The root [CLAUDE.md](../../../../CLAUDE.md) keeps only the parts that bite from outside this directory; the reasoning lives here.

- `perceptual.js` — the two non-linear slider scales. `atan` (`sliderScalingParam = 6.7975`, which is `10/atan(10)` — it exists solely to make the hardcoded ±10 track span values ±10) backs every `range` pair — wavelet/planewave brightness, and noise's levels. In all of them **`0`–`1` is calibrated to mean the full range** and the unbounded ends are the point: a `min` below 0 or a `max` above 1 eats into the bottom or saturates the top. That calibration is free for a wavelet, whose sine is bounded and hits both ends every cycle; a noise field is bell-shaped and hits nothing reliably, so `effects/noise.js` scales it explicitly (`AMPLITUDE`) to put its 1st/99th percentile on the rails. Read that comment before changing the constant — without it `0`–`1` silently means the middle of the ramp. `log` backs everything spanning decades — wavelength, the speeds, noise's scale, the glow floors — on an **integer 0…`LOG_STEPS` track**, so equal travel is equal ratio and there are no float-step artefacts; `step` in the schema does not apply to it. **`zeroable` reserves position 0 for an exact `0`** and spreads the range over 1…`LOG_STEPS`, because a log scale cannot express zero and real scenes store `freq: 0` and `glow: 0` to mean frozen / no floor. The inverse **clamps to position 1, not 0**, for a value between 0 and `min` — otherwise "nearly off" reads on the track as "off". Schema `min`/`max` are hints, not validation: values outside them render fine and the slider just pins, which is what keeps a `lambda` of 10000 intact until deliberately dragged.
- `numberFormat.js` — how a value reads in the column beside every drag control. 2dp at and above 1, but **three significant figures below it**, because the log sliders reach 0.001 and a flat 2dp renders that as `"0"` and 0.005 as `"0.01"` — a reading that looks real and isn't.
- `panelGrid.js` — frame index → grid cell. Frames arrive in **strip order**, not grid order (`di = N-1-i`), and reversing a row-major index is a 180° rotation — so anything drawing a frame must go through this. The position pad reimplemented the mapping without the reversal once and rendered upside-down under a correctly-placed handle.
- `colors.js` — just `parseHex`/`formatHex` for the hex fields (tolerates a missing `#` and the 3-digit shorthand, normalises to lowercase `#rrggbb`, returns `null` for anything else). It also held `layerSwatches`, a hardcoded per-effect switch of representative colours that both the scene cards and the effect picker drew, and that **every new effect had to be added to** — miss a case and its scenes were blank until you opened them. Both now render filmstrips (scenes from their own layers, picker tiles from the effect's defaults), so the switch is gone and a new effect needs nothing here at all.
- `filmstrip.js` — decodes `GET /api/scenes/previews`: base64 → a flat frame-major `Uint8Array`, plus `fillFrame` copying one frame into caller-owned `[r,g,b]` triples so playback allocates nothing. Frames are in **strip order** like the WebSocket ones, so painting still goes through `panelGrid` via `ledPaint`'s positions — the payload carries no grid size on purpose. It is separated from the canvas work precisely so there is something testable: vitest has no canvas. `phaseFor` offsets each canvas's place in the loop by a hash of its id — see `filmstripClock.js` for why, and note it hashes the **id** rather than using grid position so a card keeps its phase when scenes are added or reordered.
- `gridReorder.js` — the index and geometry maths behind the switcher's drag-to-reorder (`components/switcher/useSceneDrag.js` owns the pointer plumbing). Nothing here reasons in rows and columns: the grid is `auto-fill` and its column count changes with the viewport, so a slot is wherever a card **actually is**, measured once at the moment the drag starts, and "one slot along" may be a row wrap. `visualIndex` and `moveItem` are two views of the same move — the order painted during the drag and the order committed on drop — and the test checks them against each other for every from/to pair, because if they ever disagree the cards visibly jump on release. `nearestSlot` measures from the *dragged card's* centre, not the pointer's: a card is far bigger than a fingertip, and opening the gap under the card is what makes the drop land where it looks like it will. Nearest-centre rather than containment so there is always an answer — in the ragged last row, in the gutters, and past the end of the grid.
- `frameRate.js` — the header pill's reading of an `/api/fps` snapshot, split out from the component so the states that are awkward to reach in a browser are testable: `idle`, a loop genuinely behind, and work crowding the frame budget. Two judgements live here. It does **not** compare against `targetFps` — the loop's 10ms `setInterval` clamps, so a healthy machine measures ~91 of a nominal 100 and a strict comparison sits permanently red; "behind" is an average frame gap over 1.33× the target, and a separate "crowded" test catches a tick eating 80% of its budget while the rate still looks fine. And a **sub-millisecond render is formatted to 2dp** (`0.02 ms`), because a healthy render at a flat 1dp is `0.0 ms` — which reads as no measurement rather than as ample headroom.
- `filmstripClock.js` — one rAF for the whole grid, not one per card, deriving the frame index from `Date.now()` rather than counting ticks, so a card scrolling into view joins mid-loop. Painters are called only on the ~10 ticks a second where the index actually changed. The index it hands out is a **shared base**; each canvas adds its own `phaseFor` offset, because one clock originally meant all 23 cards hit the loop's seam on the same tick — the page glitching in unison read as a fault, and was far more noticeable than any single card wrapping. `queueBuild` runs **one sprite sheet per frame**: six cards entering the viewport at once would otherwise stack their whole bloom render into a single frame, a visible stall exactly while scrolling.

## `ledPaint.js`

How a frame becomes pixels, for both the previews and the pad's backdrop (they were deliberately matched in relative dot size, so the look has to change in one place). An LED is drawn as a bright core plus **three octaves of glow** — halo 0.35, wash 1.2, field 4.0 × cell — summed with `lighter`. Three, because the panel photographs as two scales at once (a tight halo and a broad regional wash) and one gaussian cannot be both: it dies superexponentially, and its peak falls as 1/σ², so a wide blur is also a faint one. Summing gaussians of geometrically increasing width approximates the heavy-tailed falloff of real diffused light. The widest octave is nearly invisible per LED but every LED contributes to every point, so it is what makes a lit *region* glow.

- **`gain` is a stack count, not a brightness.** A blur puts its falloff in the alpha channel and `brightness()` only touches RGB, which is already clipped for anything near white — it measures as a complete no-op. Drawing the blurred layer additively n times scales linearly with no ceiling. Each octave is blurred **once** into a temp canvas and then stacked as plain blits, so extra gain is nearly free; re-running the filter per draw would pay for the blur every time.
- Callers pass their own **positions array** (flat `[x0,y0,…]`, frame-index order) rather than a grid, because the pad's LEDs run through `worldToPad` and are not evenly spaced once zoomed. Every length is a factor of one LED cell, so one constant set holds at 30px cells (stage), 20 (pad), 10 (card) and 4 (thumbnails).
- Two guards that must not be dropped: below `minCellPx` it falls back to flat (a sub-pixel core is just a dimmer dot — the layer thumbnails rely on this and render pixel-identically to the old path), and **`ctx.filter` is detected with `'filter' in ctx`**. **Never detect it by assigning a value and reading it back** — that is the bug that shipped. **WebKit has no `ctx.filter` at all**, on iOS *and* macOS (unimplemented from 2019, landed behind an experimental control in 2024, still absent in Safari 27 — measured on both), so the assignment merely creates an expando that reads back as written and the check reports success on the engines with no blur. The octaves then stacked *unblurred* discs at a combined gain of 4.9x and clipped a fifth of the image to white, silently, on every Safari. `in` is sufficient because WebKit's runtime-enabled features **remove** the attribute rather than leaving it inert; it would not catch an engine that had the property and ignored it, which no engine does.
- **A missing blur means flat, and there is no third option** — this was measured, not assumed. A separable box blur in JS costs 294ms a frame on the phone at card size and 31.7s to build one filmstrip. A `drawImage` mip pyramid *is* fast enough (2.2ms, matching what the phone already pays) but cannot reproduce the widest octave: it loses light once its levels are a few px across (a level-7 chain on 900x240 kept 30% of it) and it clamps at the canvas edge where a real blur spills off and is lost, so the same calibration runs bright on a card and dark on the stage. A single large downscale is worse still — the cores canvas is sparse discs and a 64x reduction samples straight through the gaps, returning nothing.
- Anything drawn **after** the LEDs must sit outside the additive pass — the pad's zone labels and panel outline blow out under `lighter`.

## `xyPad.js`

Pad geometry, with a zoom step per zone: `panel`, `near` (one ring), `far` (a second, compressed ring). Each ring is a **fixed world-unit width on all four sides**, which keeps one scale on both axes so the drag direction is the value's direction — an aspect-matched ring skews corner drags by tens of degrees. Constant width means **each level has its own aspect ratio** (3.75 / 1.92 / 1.55), so the pad's height changes with zoom; `aspectRatio` is set inline from `padGeometry`. The panel is framed on its **cell box** (`boxX`/`boxY` — half an LED pitch beyond the centres in `xRange`/`yRange`), matching how the stage frames it, so edge LEDs are whole circles and `panel` zoom is exactly the stage's 30/8; `panelX`/`panelY` stay the centres, for placing pixels and for the far-field threshold. Distance is a rectangular offset `max(|u|-boxX, |v|-boxY)` so its contours *are* the rings. Across the far ring the whole vector is scaled by `L^(τ²)`, `L = farLimit/halfX`: exponential so reach spreads across the drag instead of bunching in the last pixels, `τ²` so `m'(0)=0` and the seam is C¹, and `m(1)=L` exactly so the edge lands on `farLimit` with nothing to clamp. `padScale` inverts by bisection — the mapping is defined on the screen offset, and only the handle ever needs the inverse.
